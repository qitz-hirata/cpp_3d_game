Design Pattern

最重要設計思想：DxLib隔離パターン

ビルドの競合を防ぎ、クリーンなC++標準コードを守るためのモジュール化アプローチ。

隔離する理由とメリット

DxLib.h は内部で Windows API の主要ヘッダである <windows.h> をインクルードします。これにより、min や max などの競合を引き起こしやすいマクロが定義され、C++標準ライブラリ（特に <algorithm> など）と名前衝突を起こします。

本プロジェクトでは、すべてのDxLib依存APIを DxLibCommon にのみインクルードさせ、他のクラスからは間接的にラップされたAPIを実行する手法を採用しています。

アーキテクチャの境界

main.cppやPlayer.cppなどの各種ゲームオブジェクトは、DxLibCommon.hに定義されたAPIのみを参照し、DxLib.hのヘッダをインクルードしません。

設計上のメモ

Cube クラスは GameObject をメンバに持っており、GameObject も Transform を持っていますが、Cube 自体も独立した Transform メンバを持っています。これは描画や位置指定時に Cube 側の Transform が直接参照される実装になっています。

Collision System

当たり判定（衝突検出）の二重系

パフォーマンスとイベント処理の柔軟性を両立するための並行システム設計。

1. マネージャーによる簡易判定

EnemyManager::Update から直接 BulletManager::CheckAndKillAllyHit を呼び出し、AABBによる重なりをその場で計算してライフ（isAlive_）を操作しています。

用途: 弾丸や敵など、大量に生成されて即座の破棄・ヒットポイント減少のみを必要とする動的オブジェクト同士の判定に最適です（オーバーヘッドが極小）。

2. CollisionManager によるイベント駆動判定

任意の Cube を CollisionManager::Register に登録することで、登録された全てのCube間で毎フレーム CheckAABB が走り、onCollisionEnter などのイベントコールバックを相互に実行します。

用途: プレイヤーと地形や障害物など、衝突の瞬間（Enter）や離脱（Exit）に複雑なイベントロジックを実行したいオブジェクトの制御に最適です。

設計ガイドライン CLAUDE.md との乖離点（注意）

CLAUDE.md には「Transform.h で <vector> をインクルードしてはいけない。MSVC の STL が std::transform を引き込み、メンバ名 transform と競合してコンパイルエラーになる」と警告が記載されています。

しかし現在の Transform.h の実装では #include <vector> および std::vector<Transform*> children が記述されています。現状でビルドが通っていても、将来的に環境が変わった際に std::transform と衝突してビルドエラーとなる可能性があるため、注意が必要です。
